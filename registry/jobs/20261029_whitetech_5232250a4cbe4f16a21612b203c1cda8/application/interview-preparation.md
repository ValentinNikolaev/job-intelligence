# WhiteTech interview preparation

## Recruiter / HR Screening

Present the candidate as a backend engineer and technical lead with PHP, Symfony and Go experience. Explain recent PHP consulting at CRURATED, then describe production integration ownership and backend performance leadership. Keep the historical Software Developer titles intact. A senior headline communicates the supported target level without rewriting employment history.

Prepare an accurate account of the most recent PHP and Symfony code personally written. Name the components, framework responsibilities and production context you can defend. The role asks for deep Symfony and Doctrine expertise, so do not substitute a general years-of-PHP answer for specific framework experience. Doctrine is not established in the selected record.

Confirm Rome as the location and ask how CET flexibility is implemented. Reconfirm earliest start, notice period, compensation expectations and Italy contracting terms before giving exact answers. Use upper-intermediate English consistently with the CV and practise explaining a technical design aloud. Describe CRURATED as concurrent part-time consulting. State the confirmed August 2026 Simple App employment end, keeping later project work distinct from an extension of employment.

## Culture Fit / Behavioral Interview

Prepare six grounded examples. For each, identify the original problem, the candidate's personal contribution, shared responsibility, the technical decision and the supported consequence. Do not invent an argument, incident or business outcome to fit a STAR template.

- How did you handle a security-sensitive decision? Use telephony architecture, privacy controls and formal review, distinguishing backend ownership from the frontend and SRE contributions.
- When did you connect systems with different assumptions? Use Crutrade authentication, account linking and purchase-ownership checks. Preserve the actual product context rather than calling it payment processing.
- What did you simplify? Explain the Snowflake processing consolidation and why repeated history reads mattered operationally.
- How did you improve a team's delivery? Use airSlate leadership and the confirmed delivery consequences, avoiding sole credit for team work.
- When did you establish an integration boundary? Use the helpdesk gateway's common model and provider adapters, with the B2B demonstration as the recorded consequence.
- How did you make a data capability easier to extend? Use CRURATED's modular event streams and shorter onboarding, explaining the source of the observed improvement.

For conflict and failure questions, select an actual remembered case before rehearsal. A technically sound hypothetical answer should remain labelled hypothetical instead of becoming candidate history.

## Technical Interview

High priority: PHP and Symfony. Review service configuration, dependency injection, request handling, validation, error mapping, transaction boundaries and asynchronous work. Prepare one concrete example of framework use from personal work. Review Doctrine's identity map, unit of work, lazy loading, migrations and query behaviour as preparation topics, while being clear about which parts were personally used in production.

High priority: SQL and data modelling. Practise explaining indexes, query plans, joins, transactions, locks, constraints and schema changes. Use airSlate's database-load and API work to show how a problem was investigated, with Prometheus as the stated measurement basis. Do not claim that the recorded result was PostgreSQL-specific. Design a small account or operation model and explain the invariants it must preserve.

High priority: integration architecture. Trace a request through authentication, provider communication, state changes, logging and recovery. Discuss idempotency keys, duplicate callbacks, timeouts, retries and reconciliation as design choices. The Crutrade example establishes account linking and purchase-ownership checks, not an acquirer implementation. Avoid inventing transaction volumes or settlement responsibilities.

High priority: architectural vocabulary. Explain DDD bounded contexts, aggregates and domain events, CQRS read/write separation, and Event Sourcing as a persisted event history with replay and projection concerns. Then distinguish these from ordinary event-driven messaging. The CV supports event-system delivery. It does not substantiate advanced production experience in every advertised pattern. Review when a simpler design would be preferable and what evidence would justify added complexity.

High priority: testing. Design an integration-test strategy around real component boundaries, controlled provider responses and database state. Cover duplicates, failed callbacks, partial success, timeouts and schema compatibility. Review PHPUnit, Codeception and Behat because the employer names them, but identify personal usage honestly. Test terminology and a list of libraries are weaker than an explanation of what a failing test detects.

Medium priority: infrastructure and delivery. Review Kubernetes workloads, readiness, configuration, secret handling, rollout safety and monitoring. Prepare Docker concepts and Jenkins pipeline structure as gap-focused study. Do not use the withdrawn airSlate migration as an example. Medium priority: security and auditability, including data minimisation and access control. Low priority: detailed regulatory interpretation outside the role's evidenced engineering responsibilities. Avoid claiming certification or compliance authority from exposure to sensitive systems.

## CV Deep-Dive Questions

Expect questions about why the telephony privacy boundary was chosen, what formal review required and what the candidate personally owned before release. Keep the description at architecture and user-risk level before supplying implementation detail. Explain the completed employment chronology separately if asked.

For customer-data workflows, explain how exports, deletions and cancellations crossed services and what administrators could do afterward. For the gateway, explain vendor-specific adapters and the shared contract. For CRURATED, distinguish account linking, collection exchange and ownership verification from payment processing. For airSlate, identify the team contribution, what Prometheus measured and how database, API, release and delivery-rate outcomes differed. Do not recite numbers without their scope or measurement basis.

## Company-Specific Preparation

Use the verified WhiteTech website and the supplied vacancy. The company describes a modular platform serving PSPs, neobanks and Open Banking providers, with payment routing and operational workflows. Prepare a hypothetical discussion of maintaining consistency across providers and making failures diagnosable. Frame it as reasoning about the product context, not knowledge of private architecture or a claim to have used the product.

## Preparation Plan

Must prepare before screening: recent PHP/Symfony examples, an honest framework-depth assessment, chronology and practical availability. Before the technical stage: review Doctrine and the advertised architecture patterns, practise a SQL investigation and an integration-failure design. Before final or culture discussions: rehearse the six real stories and the limits of personal ownership. Check the actual employer form before deciding whether a letter is required.

## Questions to Ask

2. Which advertised architecture patterns are already used in production?
3. What would this role own across provider integrations and operational support?
4. How are data consistency and reconciliation responsibilities divided?
5. Which integration failures currently consume the most engineering time?
6. How are tests and release decisions organised across teams?
7. What are the Italy contracting options and expected CET overlap?
