## Culture Fit / Behavioral Interview

Prepare eight likely questions with real evidence and honest boundaries.

1. Tell us about a problem that crossed an application and its data layer. Use airSlate database bottleneck removal and workload redistribution. Explain the observed behavior, investigation and resulting stability without inventing an outage duration.
2. When did an operational question need engineering follow-up? Use the Go support platform and collaboration with support colleagues. Identify an actual remembered case rather than assume the source supplies a customer story.
3. How do you act when you do not know an unfamiliar component? Prepare a real example of reading code and asking for help. Do not turn the absence of a recorded anecdote into a fabricated Vitess investigation.
4. How did you explain an architectural boundary? Use the vendor-neutral gateway, contract and adapter responsibilities, and the first business demo.
5. What did you simplify in a running system? Use Snowflake pipeline consolidation, eliminated history reads and continuity of service.
6. When did you take responsibility for a security-sensitive release? Use telephony architecture, formal review and collaboration with frontend and SRE.
7. How did you coordinate a performance result delivered by a team? Use airSlate API work and distinguish backend leadership from sole implementation.
8. How did you support another team's change? Use parallel CRURATED event versions as a capability for analytics migration, not proof that every consumer completed a migration.

For STAR preparation, write the known context, your actual responsibility, a concrete action and the source-backed consequence. Add remembered details only if you can defend them. Never invent an angry customer, conflict or heroic incident recovery to make a story dramatic.

## Technical Interview

High Priority: PostgreSQL and MySQL performance. Review execution plans, index selection, cardinality, joins, transactions, locking, isolation and connection pools. Practice separating application concurrency from query cost and server-resource pressure. Explain what would be measured before changing a query or index. Do not imply that application optimization proves every engine-internals detail.

High Priority: production diagnosis. Work from symptom and timeline to hypotheses, evidence and safe mitigations. Discuss logs, metrics, traces, error rates, query behavior and application changes. Explain how you would reproduce a problem and distinguish correlation from cause. Use Prometheus and Grafana familiarity honestly, without inventing prior access to PlanetScale diagnostics.

High Priority: Kubernetes and application connections. Review pod lifecycle, readiness, resource limits, networking, secrets and how a rolling deployment affects database connections. Prepare Go and PHP examples of connection reuse, timeouts, transaction boundaries and retry risks.

High Priority: customer communication under pressure. Practice an initial response, an uncertainty-aware update and an engineering escalation. Each should separate confirmed facts, working hypotheses, requested evidence and the next update. Avoid promising an unverified recovery time. Discuss when to push back respectfully on an unsafe change or request outside the available evidence.

Medium Priority: Vitess concepts, sharding, routing, schema changes, replication and failover. Learn enough to ask precise questions while stating the current experience boundary. Medium Priority: cloud infrastructure, safe data collection and escalation privacy. Medium Priority: coding exercises that inspect an unfamiliar client or reproduce a failure. Low Priority: unrelated frontend frameworks or algorithm trivia unless the employer identifies them as part of the process.
